# 02 架构与模块设计（v0.3.1）

> 状态：技术栈已定稿（MySQL + FastAPI + Vue3）。下一步细化数据表 DDL 与接口规范。

## 1. 总体架构

> 端形态定稿（2026-10-12 修订）：客户端 = **响应式网页端**（总部后台 / 门店工作台 / 司机工作台，手机浏览器可用）+ **Windows 桌面壳**（Electron 包装同一网页，最小维护）。不做小程序。
> API 为端无关的 REST + JWT，未来加小程序 / 安卓 / iOS 客户端时后端零改动，只增客户端。

```
[网页端（Vue3 响应式）] [Windows 桌面壳（Electron 包装网页）]
        └──→ API 网关（鉴权，JWT）
               └──→ 业务服务：主数据 / 要货 / 库存 / 配送 / 结算
                        └──→ MySQL
[智能体服务] ──DeepSeek API──→ 要货建议 / 配货计划（只建议，不落账）
[对接层] ──→ 银豹POS(进流水) / 金蝶(出凭证) / 管家婆(过渡对账)
```

## 2. 一期模块（12 周）
1. 主数据：门店、SKU、价目表、批次
2. 要货：建议单生成 → 店长确认 → 提交
3. 汇总与分拣：按门店汇总 → 分拣单
4. 配送与签收：配送单 → 司机工作台（网页） → 电子签收
5. 结算与核算：对账单 → 门店盈亏核算 → KPI 指标
6. 智能体：要货助手、配货计划助手
7. 对接层：银豹 / 金蝶 / 管家婆

## 3. 核心数据模型骨架
门店 store / 商品 SKU / 批次库存 / 价目表 / 要货单+明细 / 汇总单 / 分拣单 / 配送单 / 签收 / 报损 / 对账单。
**所有业务单据必须带：门店、SKU、数量、单位、批次号、时间、操作人。**

## 4. 已定设计决策
- 确定性内核 + LLM 薄层；智能体建议须店长确认才生效，全程留痕。
- 保质期/批次全链路可追溯（FIFO 严格）。
- 门店维度贯穿一切单据 → 支撑独立盈亏核算与 KPI。
- 动态扩容：无状态容器 + 多副本 + 云托管数据库。
- 新老系统双轨并行 2–4 周对账一致后切换。
- 会员自研放二期，一期不碰。

## 5. 已定稿技术栈（2026-10-12）
- 后端：FastAPI（Python）；前端：Vue3（Element Plus，响应式）；数据库：MySQL
- 客户端：网页端三合一工作台（总部/门店/司机，手机浏览器可用）+ Electron 桌面壳（Windows）；不做小程序

- 团队模型：开发由 CTO + AI 完成；实习生全程观察、阅读沉淀文档（面试用途）

## 7. 数据表设计（DDL 草案）

> **修订说明（v0.3.1）**：本版针对交叉评审发现的 6 项设计差距修订，表数量 22 张 → 26 张：
> ① 新增 `batch_flow` 批次流水台账——每次批次变动（收货加 / 分拣减 / 报损减 / 盘点调整）一行，带关联单据类型、单据号、操作人、时间；`batch_stock` 保留为结存表，两者在服务层同一事务写入。设计理由：**可追溯 = 流水 + 结存双轨**。
> ② 修复软删除与唯一索引冲突：全部软删表的业务编码唯一索引（`uk_store_no` / `uk_sku_no` / `uk_supplier_no` / 幂等键等）改为与 `deleted_at` 组合，且 `deleted_at` 改为 `NOT NULL DEFAULT '1970-01-01 00:00:00'`（原因见下方通用约定「软删除坑」）。
> ③ 新增 `permission`（权限点，如 `order:create` / `stock:adjust` / `agent:apply`）与 `role_permission`（角色×权限点多对多）；§8 的四角色改述为「角色是权限点集合」。
> ④ `idempotency_key` 在全部写单据头表落唯一索引（同样与 `deleted_at` 组合）：purchase_order / order_head / summary / pick / delivery / sign / loss / reconcile / agent_suggestion。
> ⑤ 新增 `agent_suggestion` 建议快照表（suggestion_type、依据 JSON、apply 状态、生成时间、关联 order_id），原 `order_head.agent_advice` 迁移过去；§8 智能体端点路径不变，仅落库位置改变。
> ⑥ 统一每表索引理由注释格式为 `-- 索引: 列名 用途: 一句话`。
> 边界不变：智能体「只建议、不落账」依旧成立——建议快照写入 `agent_suggestion` 只是留痕，不生成有效单据、不动库存与结算。

> 通用约定：引擎 InnoDB、utf8mb4；审计四字段 created_by/created_at/updated_by/updated_at（表内不再赘述）；
> **软删除**：`deleted_at DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00'`，哨兵值 `1970-01-01 00:00:00` = 未删除，其余值 = 删除时间。**坑（必读）**：MySQL 唯一索引中 NULL 互不相等、完全不参与约束；若沿用 `deleted_at DATETIME DEFAULT NULL`，则 `(store_no, deleted_at)` 里所有"未删除行"的 deleted_at 都是 NULL，同一编码可无限重复插入而不报错，唯一性形同虚设。改用 NOT NULL 哨兵值后组合唯一索引才真正生效，且软删后同一业务编码可重新启用（历史行仍留档）。
> **幂等**：`idempotency_key VARCHAR(64) DEFAULT NULL` + `UNIQUE KEY uk_idem (idempotency_key, deleted_at)`；不传键时值为 NULL（唯一索引不约束，等价"本次不启用幂等"），同键重复提交由唯一索引兜底、返回首次结果。
> **索引注释**：统一格式 `-- 索引: 索引名(列名, ...) 用途: 一句话`；`PRIMARY KEY(id)` 为自增聚簇索引、全表一致，故仅对"没有二级索引"的表注释主键。
> 数量三件套 qty_base（基础单位数值，计算用）/ qty_unit（展示单位数值）/ unit（展示单位名），换算在服务层按 sku.convert_factor 统一；
> 并发控制 = 单据头 version 乐观锁 + 库存扣减 SELECT ... FOR UPDATE 行锁；
> 不建物理外键（逻辑外键 + 服务层校验），理由：大表性能、云 RDS 在线 DDL、未来分库分表与单据归档；
> store_id=0 约定为总部仓；金额 DECIMAL(14,2)、数量 DECIMAL(14,3)、单价 DECIMAL(12,4)。

### 7.1 主数据

```sql
CREATE TABLE store (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  store_no       VARCHAR(32)  NOT NULL COMMENT '门店编码',
  name           VARCHAR(64)  NOT NULL COMMENT '门店名称',
  region         VARCHAR(64)  DEFAULT NULL COMMENT '区域/城市',
  address        VARCHAR(255) DEFAULT NULL,
  contact_name   VARCHAR(32)  DEFAULT NULL,
  contact_phone  VARCHAR(32)  DEFAULT NULL,
  delivery_cycle ENUM('daily','every_other_day') NOT NULL DEFAULT 'daily' COMMENT '配送节奏:日配/隔日配',
  status         TINYINT NOT NULL DEFAULT 1 COMMENT '1营业 0停业',
  created_by     BIGINT UNSIGNED DEFAULT NULL,
  created_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by     BIGINT UNSIGNED DEFAULT NULL,
  updated_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at     DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00' COMMENT '软删除时间,哨兵值=未删除',
  PRIMARY KEY (id),
  UNIQUE KEY uk_store_no (store_no, deleted_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='门店';
-- 理由: ① store_no 业务编码唯一,软删除不删行,历史单据仍可关联; ② delivery_cycle 决定门店要货节奏,驱动每日汇总定时任务。
-- 索引: uk_store_no(store_no, deleted_at) 用途: 门店编码在"未删除行"内唯一,软删后可重开同一编码。

CREATE TABLE supplier (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  supplier_no   VARCHAR(32) NOT NULL,
  name          VARCHAR(64) NOT NULL,
  contact_name  VARCHAR(32) DEFAULT NULL,
  contact_phone VARCHAR(32) DEFAULT NULL,
  payment_terms INT NOT NULL DEFAULT 0 COMMENT '账期(天)',
  status        TINYINT NOT NULL DEFAULT 1,
  created_by BIGINT UNSIGNED DEFAULT NULL, created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by BIGINT UNSIGNED DEFAULT NULL, updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00' COMMENT '软删除时间,哨兵值=未删除',
  PRIMARY KEY (id),
  UNIQUE KEY uk_supplier_no (supplier_no, deleted_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='供应商';
-- 理由: payment_terms 账期驱动应付与对账周期;与采购单逻辑关联 supplier_id。
-- 索引: uk_supplier_no(supplier_no, deleted_at) 用途: 供应商编码在未删除行内唯一,软删后可复用编码。

CREATE TABLE sku (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  sku_no         VARCHAR(32) NOT NULL,
  name           VARCHAR(64) NOT NULL COMMENT '品名',
  category       VARCHAR(32) NOT NULL COMMENT '馅料-肉馅/馅料-海鲜/面皮/调料/包材/鲜活',
  spec           VARCHAR(64) DEFAULT NULL COMMENT '规格描述,如5kg/袋',
  unit           VARCHAR(16) NOT NULL COMMENT '订货/展示单位,如袋',
  base_unit      VARCHAR(16) NOT NULL COMMENT '基础计算单位,如kg',
  convert_factor DECIMAL(12,4) NOT NULL DEFAULT 1 COMMENT '1订货单位=多少基础单位',
  shelf_life_hours INT NOT NULL COMMENT '保质期(小时)',
  supply_type    ENUM('direct','temp') NOT NULL DEFAULT 'direct' COMMENT '直配/临采',
  status         TINYINT NOT NULL DEFAULT 1,
  created_by BIGINT UNSIGNED DEFAULT NULL, created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by BIGINT UNSIGNED DEFAULT NULL, updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00' COMMENT '软删除时间,哨兵值=未删除',
  PRIMARY KEY (id),
  UNIQUE KEY uk_sku_no (sku_no, deleted_at),
  KEY idx_category (category)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='商品SKU';
-- 理由: ① base_unit+convert_factor 统一解决多单位换算,库存与单据数量一律按基础单位计算,展示单位仅用于显示; ② shelf_life_hours 支撑批次效期与临期预警; ③ supply_type 区分统采统配与临采报备流程。
-- 索引: uk_sku_no(sku_no, deleted_at) 用途: SKU 编码在未删除行内唯一,软删后可复用编码。
-- 索引: idx_category(category) 用途: 总部按品类筛选与统计(B端列表默认筛选)。

CREATE TABLE price (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  sku_id         BIGINT UNSIGNED NOT NULL COMMENT '逻辑外键→sku.id',
  price_type     ENUM('purchase','transfer') NOT NULL COMMENT '采购价/内部调拨价',
  price          DECIMAL(12,4) NOT NULL COMMENT '单价(元/订货单位)',
  effective_from DATE NOT NULL,
  effective_to   DATE DEFAULT NULL COMMENT 'NULL=现行有效',
  created_by BIGINT UNSIGNED DEFAULT NULL, created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by BIGINT UNSIGNED DEFAULT NULL, updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00' COMMENT '软删除时间,哨兵值=未删除',
  PRIMARY KEY (id),
  UNIQUE KEY uk_sku_type_from (sku_id, price_type, effective_from, deleted_at),
  KEY idx_sku_eff (sku_id, effective_from, effective_to)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='价目表(含历史版本)';
-- 理由: ① 价格带生效区间、只增不改——对账必须能取任意历史日期的当时价格; ② purchase/transfer 两类价分别支撑采购核算与门店内部结算(纯直营=内部核算价)。
-- 索引: uk_sku_type_from(sku_id, price_type, effective_from, deleted_at) 用途: 同一SKU同类型价在同一天只允许一条有效记录,软删后可重录。
-- 索引: idx_sku_eff(sku_id, effective_from, effective_to) 用途: 按日期区间取"当时价"的对账查询路径。
```

### 7.2 库存与采购

```sql
CREATE TABLE batch_stock (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  store_id   BIGINT UNSIGNED NOT NULL COMMENT '0=总部仓,其余=门店ID',
  sku_id     BIGINT UNSIGNED NOT NULL,
  batch_no   VARCHAR(32) NOT NULL COMMENT '批次号,追溯主键',
  qty_base   DECIMAL(14,3) NOT NULL DEFAULT 0 COMMENT '结存数量(基础单位)',
  produced_at DATE DEFAULT NULL COMMENT '生产日期',
  expire_at  DATETIME NOT NULL COMMENT '保质期至',
  version    INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '乐观锁版本',
  created_by BIGINT UNSIGNED DEFAULT NULL, created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by BIGINT UNSIGNED DEFAULT NULL, updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00' COMMENT '软删除时间,哨兵值=未删除',
  PRIMARY KEY (id),
  UNIQUE KEY uk_store_sku_batch (store_id, sku_id, batch_no, deleted_at),
  KEY idx_expire (expire_at),
  KEY idx_sku_store (sku_id, store_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='批次库存(结存表)';
-- 理由: ① (store_id,sku_id,batch_no) 唯一:库存按门店×批次隔离; ② expire_at 索引支撑临期预警与 FIFO 出库(ORDER BY expire_at); ③ version 乐观锁防并发扣减,服务层叠加行锁兜底; ④ 本表只是"当前结存"快照,任何变动必须同时写 batch_flow 流水——只改结存无法回答"为什么是这个数、依据哪张单、谁改的"。
-- 索引: uk_store_sku_batch(store_id, sku_id, batch_no, deleted_at) 用途: 门店×SKU×批次唯一锁定结存行,供 SELECT ... FOR UPDATE 行锁扣减。
-- 索引: idx_expire(expire_at) 用途: 临期预警扫描与 FIFO 出库排序。
-- 索引: idx_sku_store(sku_id, store_id) 用途: 按SKU横向看各门店/仓库存分布。

CREATE TABLE batch_flow (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  store_id        BIGINT UNSIGNED NOT NULL COMMENT '0=总部仓,其余=门店ID',
  sku_id          BIGINT UNSIGNED NOT NULL,
  batch_no        VARCHAR(32) NOT NULL COMMENT '批次号,与 batch_stock.batch_no 同源',
  flow_type       ENUM('receive_add','pick_sub','loss_sub','count_adjust') NOT NULL COMMENT '收货加/分拣减/报损减/盘点调整',
  qty_change_base DECIMAL(14,3) NOT NULL COMMENT '变动量(基础单位):加为正、减为负',
  qty_after_base  DECIMAL(14,3) NOT NULL COMMENT '本次变动后结存(基础单位),与 batch_stock.qty_base 逐笔对账',
  expire_at       DATETIME DEFAULT NULL COMMENT '变动时点的效期快照,避免后续改期影响历史还原',
  doc_type        ENUM('purchase_order','pick','loss','stock_count','other') NOT NULL COMMENT '关联单据类型',
  doc_id          BIGINT UNSIGNED DEFAULT NULL COMMENT '关联单据头id(逻辑外键)',
  doc_no          VARCHAR(32) NOT NULL COMMENT '关联单据号,人可读的追溯入口',
  doc_item_id     BIGINT UNSIGNED DEFAULT NULL COMMENT '关联单据明细id,定位到行',
  operate_by      BIGINT UNSIGNED NOT NULL COMMENT '操作人(逻辑外键→user.id)',
  occurred_at     DATETIME NOT NULL COMMENT '业务发生时间(非写入时间)',
  remark          VARCHAR(255) DEFAULT NULL,
  created_by BIGINT UNSIGNED DEFAULT NULL, created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by BIGINT UNSIGNED DEFAULT NULL, updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_flow_source (doc_type, doc_no, flow_type, store_id, sku_id, batch_no),
  KEY idx_store_sku_batch (store_id, sku_id, batch_no, occurred_at),
  KEY idx_doc (doc_type, doc_no),
  KEY idx_operate (operate_by, occurred_at),
  KEY idx_occurred (occurred_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='批次流水台账(收货/分拣/报损/盘点每次变动一行)';
-- 理由: ① **可追溯 = 流水 + 结存双轨**:batch_flow 记录"每一笔变动"(加/减/调整、谁操作、依据哪张单),batch_stock 只保存"当前结存";单看结存无法解释数量来源,单看流水查询又要全表求和,两者互补; ② **同一事务写入**:服务层在扣减/增加 batch_stock 的同一事务内插入 batch_flow,任一方失败整体回滚,两表恒等(对任意 store_id+sku_id+batch_no,batch_stock.qty_base = SUM(batch_flow.qty_change_base)),可作为日终对账等式; ③ **仅追加 append-only**:无 deleted_at、不提供 UPDATE/DELETE 接口,记错只能写反向冲正流水,满足审计不可篡改要求; ④ uk_flow_source 按"单据类型+单据号+动作+批次"防同一单据重复入账(网络重试幂等); ⑤ 报损/盘点调整(qty_change_base 可正可负)同样走本表,库存去向永远可解释。
-- 索引: uk_flow_source(doc_type, doc_no, flow_type, store_id, sku_id, batch_no) 用途: 同一来源单据的同一行同一动作只能记一笔流水,防重复入账。
-- 索引: idx_store_sku_batch(store_id, sku_id, batch_no, occurred_at) 用途: 按门店×SKU×批次拉时间序流水,批次追溯的主查询路径。
-- 索引: idx_doc(doc_type, doc_no) 用途: 由单据号反查其对库存的全部影响行,审计与对账常用。
-- 索引: idx_operate(operate_by, occurred_at) 用途: 按操作人审计其一段时间内的库存动作。
-- 索引: idx_occurred(occurred_at) 用途: 按时间窗统计进出量(日/周流水、对账期汇总)。

CREATE TABLE purchase_order (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  po_no          VARCHAR(32) NOT NULL,
  supplier_id    BIGINT UNSIGNED NOT NULL,
  store_id       BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '收货点,0=总部仓',
  status         ENUM('draft','submitted','received','cancelled') NOT NULL DEFAULT 'draft',
  expect_at      DATETIME DEFAULT NULL COMMENT '预计到货',
  idempotency_key VARCHAR(64) DEFAULT NULL COMMENT '幂等键',
  version        INT UNSIGNED NOT NULL DEFAULT 0,
  created_by BIGINT UNSIGNED DEFAULT NULL, created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by BIGINT UNSIGNED DEFAULT NULL, updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00' COMMENT '软删除时间,哨兵值=未删除',
  PRIMARY KEY (id),
  UNIQUE KEY uk_po_no (po_no, deleted_at),
  UNIQUE KEY uk_idem (idempotency_key, deleted_at),
  KEY idx_supplier_status (supplier_id, status)
```

### 7.7 表关系一览

```
supplier ── purchase_order ── purchase_order_item ──(收货,同事务)→ batch_stock + batch_flow(receive_add)
store ──┬─ order_head ── order_item
        ├─ batch_stock(store_id 维度,结存) ── batch_flow(每次变动一行,流水)
        ├─ agent_suggestion(apply 后回指 order_head) ──(采纳)→ order_head(source=agent)
        ├─ pick / delivery / sign
        ├─ loss / reconcile
sku ── price / batch_stock / 各单据明细
summary(require_date 唯一) ── summary_item(SKU×总量)
summary ── pick(按门店) ── pick_item(批次落定) ──(FIFO 扣减,同事务)→ batch_stock + batch_flow(pick_sub)
pick ── delivery ── delivery_item(→pick_item 溯源) ── sign(1:1) ── sign_item(差异)
loss ──(审批通过,同事务)→ batch_stock + batch_flow(loss_sub/count_adjust)
user ── user_role ── role ── role_permission ── permission
```

**核心单据链**：要货单(order) → 汇总单(summary) → 分拣单(pick) → 配送单(delivery) → 签收单(sign) → 对账单(reconcile)。
**批次线**：收货入 batch_stock（并写 batch_flow 流水）→ 分拣落批次（写减量流水）→ 签收确认 → 报损/盘点扣减（写减量/调整流水），批次号全程贯穿；对任意 (store_id, sku_id, batch_no) 恒有 `batch_stock.qty_base = SUM(batch_flow.qty_change_base)`，可作日终对账等式。

## 8. REST API 规范

### 8.1 通用约定
- 基址 `/api/v1`，请求/响应均为 JSON，UTF-8。
- 统一响应：`{ "code": 0, "message": "ok", "data": {...} }`；错误码分段：`0` 成功 / `40000` 参数校验失败 / `40100` 未认证 / `40300` 无权限(缺权限点或超数据范围) / `40400` 资源不存在 / `40900` 状态冲突(状态机非法流转/乐观锁冲突/幂等键重复) / `42900` 限流 / `50000` 服务端错误。
- 鉴权：请求头 `Authorization: Bearer <JWT>`。**判定单元是权限点（permission.code，如 `order:create` / `stock:adjust` / `agent:apply`），角色（role）只是权限点集合**——`role_permission` 承载角色×权限点多对多，用户的有效权限 = 其全部角色权限点的并集；`40300` 由"所需权限点 ∉ 并集"触发。四个内置角色 `admin` 总部管理员 / `ops` 总部运营与仓配 / `driver` 司机 / `store_manager` 店长，即四组预置权限集（清单见 §8.3）；新增岗位只需新增权限集，不改判定逻辑。数据范围：`user.store_id` 非空时所有查询强制注入本店条件——权限点管"能做什么动作"，store_id 管"对哪些数据做"，两者正交。
- 幂等：写接口支持请求头 `Idempotency-Key`（≤64 字符），落 `idempotency_key` 列并建 `uk_idem(idempotency_key, deleted_at)` 唯一索引兜底；重复请求返回首次结果（`40900` 仅在键相同但请求体不一致时返回）。覆盖全部写单据头表：purchase_order / order_head / summary / pick / delivery / sign / loss / reconcile，以及 agent_suggestion；签收单无软删，其 `uk_idem` 只含 `idempotency_key`。
- 分页：`?page=1&page_size=20`（max 200），响应 `data: { list, total, page, page_size }`。
- 留痕：写操作一律落 created_by/updated_by；状态变更落 confirm_by 等专属字段；关键操作另有操作日志。库存变动同时落 `batch_flow` 流水（操作人 + 关联单据），做到"结存有数、流水有据"。
- 时间：`DATE` 格式 YYYY-MM-DD（如 require_date=2026-10-13），时间戳 ISO8601。

### 8.3 权限点清单与角色映射

- **判定模型**：权限（permission）是判定单元，角色（role）是权限点集合。网关按端点取所需权限点，再看"用户全部角色的权限并集"是否包含它；`permission` 存权限点，`role_permission` 存角色×权限点多对多，`user_role` 把用户挂到角色。
- **与数据范围正交**：权限点管"能不能做这个动作"，`user.store_id` 管"对哪些门店的数据做"。例：`store_manager` 有 `order:create`，但只能为本店建单。
- **命名**：`模块:资源:动作`；与库存直接相关的动作用"效果"命名（如 `stock:adjust`）而不是表名。
- **种子数据**：`permission` 按上表初始化 38 条（37 条覆盖 §8.2 的 39 个端点，多条端点共用一个权限点；第 38 条为预留），`role_permission` 按"默认角色"列展开为授权行。
- 注：评审示例中的 `agent:confirm` 在本表落地为 `agent:apply`——语义是"店长确认采纳建议并生成 draft 要货单"，生成后仍需 `order:confirm` 才生效，避免"双重确认"歧义。
