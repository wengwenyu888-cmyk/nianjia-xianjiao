# 05 工程基座方案（v0.1）

> 状态：工程落地基线。上游依据：`docs/02-架构与模块设计.md`（技术栈已定稿）。
> 适用：单人开发 + AI 辅助，GitHub 私有仓库 + GitHub Actions CI，部署腾讯云。
> 原则：先能跑通「要货→汇总→分拣→配送→签收→对账」一条主链路，再谈横向扩展。

## 1. 单体仓库目录结构

单仓库（monorepo）三个独立可部署单元（`backend` / `frontend-web` / `desktop`），共享文档与部署脚本；客户端形态定为**响应式网页端 + Windows 桌面壳**：网页端同时服务总部后台、门店端与司机端，桌面壳用 Electron 包装同一份网页（几乎零额外业务代码）；API 保持端无关 REST，未来可扩展小程序 / 安卓 / iOS 客户端。后端分层严格遵守「api 只做协议、service 只做业务、model 只做持久化、schema 只做数据契约」。


**分层铁律（避免半年后腐化）**

- `api/` 不允许出现 SQLAlchemy 查询与业务判断，只允许「取参 → 调 service → 返回 schema」。
- `service/` 是唯一的事务边界；跨表写操作必须在一个 service 方法内完成。
- `model/` 不允许被 `api/` 直接导入；`schema/` 不允许被 `service/` 之外的层当作入参类型。
- 对外返回一律用 schema，禁止直接返回 ORM 对象（防止字段泄露与 N+1）。

## 2. 依赖清单

### 2.1 backend（包管理器：uv）

选 uv 的理由：单个工具同时替代 pip + venv + pip-tools，安装与解析速度比 pip 快一个量级；`uv.lock` 锁定全部传递依赖，保证本地、CI、线上三方一致。

| 依赖 | 用途 | 选型理由（一句话） |
| --- | --- | --- |
| fastapi | Web 框架 | 原生 async + 自动 OpenAPI 文档，三端联调时有现成交互式接口页 |
| uvicorn[standard] | ASGI 服务器 | FastAPI 官方推荐运行器，支持热重载与多 worker |
| pydantic / pydantic-settings | 数据校验与配置 | 请求响应契约与配置项都用类型声明，错误在启动期暴露而非线上 |
| sqlalchemy 2.x | ORM | 2.0 风格类型化查询，同步链路够用且迁移成本低，生态最成熟 |
| pymysql | MySQL 驱动 | 纯 Python 驱动，免编译，容器内安装最省事 |
| alembic | 数据库迁移 | SQLAlchemy 官方迁移工具，DDL 变更可版本化、可审计 |
| cryptography | 驱动依赖 | PyMySQL 连接 MySQL 8 的 caching_sha2_password 认证需要 |
| httpx | HTTP 客户端 | 同时支持同步/异步，调用 DeepSeek API 与银豹/金蝶接口 |
| python-jose[cryptography] | JWT | 签发与校验三端登录令牌，纯 Python 实现无系统依赖 |
| passlib[bcrypt] | 密码哈希 | 口令只存哈希，绝不明文落库 |
| python-multipart | 表单/上传 | 签收照片、Excel 导入等文件上传依赖它 |
| slowapi 或自研中间件 | 接口限流 | 防登录爆破与刷单，按 IP + 账号双维度限流 |
| openpyxl | Excel 读写 | 门店台账导入导出、对账单导出，业务方强需求 |
| pytest / pytest-asyncio / httpx(TestClient) | 测试 | 单测 service、接口测试用 TestClient，CI 门禁 |
| ruff | lint + format | 一个工具替代 flake8/isort/black，速度快，规则集够用 |
| mypy（可选） | 类型检查 | 单人项目不宜过严，先只对 core/service 开基础校验 |

### 2.2 frontend-web（包管理器：pnpm）

选 pnpm 的理由：硬链接存储节省磁盘、依赖隔离严格（避免幽灵依赖），且对 monorepo 友好；配合 pnpm-lock.yaml 保证构建可复现。

| 依赖 | 用途 | 选型理由（一句话） |
| --- | --- | --- |
| vue 3 | 框架 | 组合式 API 逻辑复用清晰，与 Element Plus 是官方推荐搭配 |
| vite | 构建工具 | 冷启动与 HMR 极快，配置量小，单人开发反馈循环短 |
| element-plus | UI 组件库 | 表格/表单/日期选择器等中后台刚需组件开箱即用，中文文档完善 |
| pinia | 状态管理 | Vue3 官方推荐，API 比 Vuex 简洁，模块化天然 |
| vue-router 4 | 路由 | 官方方案，配合守卫做登录与角色权限收敛 |
| axios | HTTP 客户端 | 拦截器统一注入 Token、统一错误提示，团队惯用 |
| dayjs | 日期处理 | 体积小，API 与 moment 兼容，处理配送时效与账期足够 |
| echarts（按需） | 图表 | 汇总看板、门店盈亏趋势图，二期再做也不冲突 |
| eslint + prettier | 代码规范 | CI 中卡住格式与常见缺陷，避免人工评审 |
| unplugin-auto-import / components | 自动导入 | 减少样板 import，提升开发速度 |

## 3. GitHub Actions CI 骨架

触发：`pull_request`（目标 main）必跑；`push` 到 main 跑同套 + 构建镜像。**要点式，不写完整 yaml。**

**通用要点**

- 用 `paths` 过滤：只改 docs 不触发后端测试，节省额度。
- 并发控制 `concurrency: cancel-in-progress`，同 PR 新推送取消旧任务。
- 全部依赖装自锁文件（`uv sync --frozen` / `pnpm install --frozen-lockfile`），禁止漂移。
- 数据库用 service 容器（MySQL 8）而非 mock SQLite，避免方言差异导致线上翻车。
- 密钥只从 `secrets` 注入，不在 yaml 中写任何明文。

**Job 1：backend-lint-test**

1. `actions/checkout@v4`，`astral-sh/setup-uv@v5` 带缓存。
2. `uv sync --frozen` 装依赖。
3. `uv run ruff check .` 与 `uv run ruff format --check .` —— 不通过直接失败。
4. 启动 MySQL 8 service 容器，注入测试库环境变量。
5. `uv run alembic upgrade head` 验证迁移可执行（迁移坏掉是上线最大杀手）。
6. `uv run pytest --cov=app --cov-fail-under=60` —— 覆盖率门槛先低后升。
7. 失败时上传测试报告与日志为 artifact。

**Job 2：frontend-lint-build**

1. `pnpm/action-setup` + `actions/setup-node@v4`（开 pnpm 缓存）。
2. `pnpm install --frozen-lockfile`。
3. `pnpm lint` + `pnpm type-check`（vue-tsc）—— 类型错误在 CI 拦下。
4. `pnpm build` —— 保证生产构建可过（含环境变量缺失这类问题）。

**Job 3：docker-build（仅 push 到 main）**

1. 构建 backend 镜像，打 `sha-<commit>` 与 `latest` 双标签。
2. 推送到腾讯云 TCR 镜像仓库。
3. 部署动作放到「部署」工作流或人工触发，避免 CI 自动上生产。

**分支保护**：main 必须 PR、必须过 Job1/Job2、禁止直接 push。

## 4. 腾讯云部署方案

> **定稿（2026-10-12）**：起步用「轻量应用服务器 + Docker」单机形态（2C4G 起步），仓库名 `nianjia-xianjiao`；门店量增长后再迁 TKE。数据库用云 RDS MySQL（不随单机自建）。

**总体形态：容器化多副本无状态 + 云 RDS MySQL + CDN + 网页端与桌面端分发。**

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 计算 | TKE（容器服务）或轻量应用服务器起 Docker | 后端镜像跑 2 副本起步，无状态 |
| 数据库 | 云 RDS MySQL 8 | 自动备份、主从、故障切换，自建 MySQL 的运维成本不划算 |
| 静态资源 | COS 对象存储 + CDN | 前端 dist 与签收照片走对象存储，CDN 加速与回源 |
| 入口 | CLB / Ingress + HTTPS 证书 | 统一域名 `api.xxx.com`，强制 HTTPS |
| 镜像仓库 | TCR 个人版/企业版 | 与 Actions 打通，免密拉取 |
| 日志监控 | 云日志 CLI + 云监控告警 | 至少要有「接口 5xx 率」和「副本存活」两条告警 |

**无状态约束（能扩容的前提）**

- 进程内不存会话：JWT 自包含，不用服务端 session。
- 不写本地磁盘：上传文件直接进 COS；日志走 stdout 由云日志采集。
- 定时任务（如每日汇总）要么集中到单副本 Deployment（`replicas: 1`），要么加分布式锁，避免多副本重复跑。
- 配置全部来自环境变量 / 云密钥管理，镜像内不烘焙任何环境差异。

**发布流程**

1. CI 构建并推镜像到 TCR（标签为 commit sha）。
2. 更新 Deployment 镜像标签，滚动更新 `maxUnavailable: 0`，新副本就绪探针通过才切流量。
3. 发布前先跑 `alembic upgrade head`（用独立 Job 或一次性容器），迁移必须向后兼容一个版本（先加字段不删字段，先兼容再清理）。
4. 灰度：先 1 个副本跑新版本观察 10 分钟，无异常再全量。
5. 回滚：镜像标签回退上一版即可；数据库只做前进式迁移，回滚不依赖 DDL 回退。

**桌面安装包发布**

1. `desktop` 用 electron-builder 打 Windows nsis 安装包（`pnpm dist`，产物在 `desktop/release/`）。
2. 版本号随前端构建走：网页端与壳用同一版本号；后端接口保持向后兼容至少一个客户端版本周期（用户端更新不可控）。
3. 安装包放对象存储 COS（或 GitHub Releases），由 CDN 分发下载链接；壳加载的网页产物同样走 COS + CDN。
4. 网页端改版无需重装：壳加载的就是 CDN 上那份网页，刷新即生效；只有壳自身（Electron 版本、窗口与菜单配置）变更时才重新出安装包。
5. 未做代码签名前，Windows SmartScreen 会提示「未知发布者」——内部试用可先忽略，对外分发前再补签名。

**动态扩容落地方式（按顺序用）**

1. **加副本（首选）**：服务无状态，直接调 `replicas` 或交给 HPA 按 CPU/QPS 自动扩缩；秒级生效、成本随用量走。
2. **升配**：单副本 CPU/内存打满且 QPS 上不去（CPU 密集型，如对账批量计算）时，提升实例规格；需要重启，有分钟级中断。
3. **读写分离 / 加只读实例**：读多写少、报表与对账查询拖慢主库时，挂只读实例，报表类查询走只读连接。
4. **异步化与限流兜底**：先扩副本前应确认慢查询不是根因；对账等重任务改异步（任务表 + 轮询/队列），并对峰时接口限流保护数据库。
5. **CDN 兜流量**：静态资源与图片流量不进后端，是最便宜的一层扩容。

## 5. 本地开发环境

前置：Git、Python 3.12、uv、Node 20 + pnpm、Docker（起 MySQL）。

```bash
# 0) 取代码
git clone git@github.com:<org>/nianjia-xianjiao.git
cd nianjia-xianjiao

# 1) 配置环境变量（复制模板后填值，.env 已在 .gitignore 中）
cp .env.example .env            # Windows: copy .env.example .env

# 2) 后端
cd backend
uv sync                         # 按 uv.lock 装依赖
uv run alembic upgrade head      # 建表 / 迁移到最新
uv run uvicorn app.main:app --reload --port 8000
#   → 接口文档 http://127.0.0.1:8000/docs

# 3) 前端（新开终端）
cd frontend-web
pnpm install
pnpm dev                         # → http://127.0.0.1:5173

# 4) 桌面壳（Windows 客户端，可选；需先起第 3 步的 pnpm dev）
cd desktop
pnpm install
pnpm dev                         # 加载 http://127.0.0.1:5173
# 打包：pnpm dist → nsis 安装包输出到 desktop/release/
```

补充约定：

- 本地 MySQL 用 `docker compose -f deploy/docker-compose.dev.yml up -d` 起，避免污染本机。
- 常用命令收进 Makefile：`make dev-backend` / `make dev-web` / `make test` / `make lint`，新人（实习生）照 README 即可跑起来。
- 种子数据：`uv run python -m app.scripts.seed` 造几家门店、若干 SKU 与一张演示要货单，保证空库也能走通主链路。

## 6. 安全要点

1. **密钥不进仓库（底线）**
   - `.env`、`*.pem`、`credentials.json` 一律写进 `.gitignore`；只提交 `.env.example`（只有变量名）。
   - CI 与线上用 GitHub Secrets 与腾讯云密钥管理注入；数据库密码、JWT 密钥、DeepSeek API Key 一个都不能进代码。
   - 已误提交的密钥，改历史不够——**必须轮换该密钥**，因为克隆过的仓库无法收回。
   - 接第三方（银豹/金蝶/管家婆）的凭据单独成表加密存储，日志中脱敏打印。

2. **JWT**
   - 用 HS256 起（单服务够用），密钥至少 32 字节随机串，与数据库密码分开且可独立轮换。
   - access token 短有效期（2 小时左右）+ refresh token（7 天）；refresh 可撤销落库。
   - payload 只放 `user_id / role / store_id / exp`，不放手机号等敏感信息（JWT 只签名不加密，等于明文）。
   - 角色收敛：门店账号只能看自家 `store_id` 的数据，服务端每个查询强制带门店过滤，**绝不信任前端传的 store_id**。
   - 司机端只给「自己的配送任务」最小接口权限。

3. **接口限流与防刷**
   - 登录接口按 IP + 账号双维度限流（如 5 次/分钟），连续失败锁定一段时间，防口令爆破。
   - 要货提交、签收等写接口做幂等（客户端传唯一请求号 + 数据库唯一索引），防重复提交产生重复单据。
   - 全局限流按 IP 令牌桶，突发流量保护数据库；对账/报表这类重接口单独设更严阈值。
   - 校验一律在服务端做：数量必须为正、价目由后端取、状态流转必须合法（防止前端绕过流程直接改状态）。

4. **其他常规项**
   - CORS 白名单只放开网页端域名（总部后台 / 门店端 / 司机端）与桌面壳加载地址，禁止 `allow_origins=["*"]` 搭配凭据。
   - 生产环境关闭 `/docs` 或加鉴权；错误响应不返回堆栈与 SQL。
   - 上传文件校验类型与大小、重命名存储，防止路径穿越与可执行文件上传。
   - HTTPS 全链路；数据库不暴露公网、只允许内网白名单访问。
   - 审计留痕：单据的状态变更、智能体建议的确认动作写操作日志（谁、何时、改了什么），对账纠纷时要能追溯。
   - 日志与监控中禁止打印完整身份证/手机号/令牌，统一脱敏工具处理。

---

## 7. 落地顺序（建议）

1. 仓库骨架 + `.gitignore` + `.env.example` + Makefile + CI 两 Job 先跑绿。
2. 后端 core（config / security / deps）+ 登录接口 + 迁移打通。
3. 主数据（门店、SKU、价目）接口 + 后台列表页。
4. 主链路单据逐个上线：要货 → 汇总 → 分拣 → 配送 → 签收 → 对账。
5. 云上部署一次（哪怕只有 1 副本），把发布与回滚路径先踩熟，再谈扩容与智能体。
